GenAI Foundations & Prompt Engineering for Developers

A working model of what a language model actually does, and the prompting technique that follows from it. Everything here is aimed at one outcome: getting code you would be willing to put your name on.

Session 1 of 2 2 hours + 2 hours MERN + Java cohorts Tools: any chat LLM

By the end of the session

  • Separate tasks where AI is reliable from tasks where it is risky.

  • Use few-shot examples and constraints to get consistent, usable code.

Part 1 · Mental model

How an LLM generates output

There is no database of answers inside the model, no lookup, no compiler, no execution. There is a single repeated prediction, and everything else is a consequence of it.

Tokens: the unit the model actually sees

Text is split into tokens before the model touches it. A token is roughly a word, a word fragment, or a piece of punctuation. Common words are one token. Rare words, identifiers and non-English text split into several.

The same sentence, as a human reads it and as a model receives it
useState returns an array of two values.
useState returns an array of two values.

useState is not one thing to the model. It is two fragments that very often appear together.

Three consequences worth carrying with you:

  • Character-level tasks are unreliable. Counting letters, reversing strings by hand, or counting words are exactly the tasks the tokenisation hides from the model.
  • Token count is not word count. Code, JSON and long identifiers consume more tokens than prose of the same length.
  • Tokens are the billing and limit unit. Everything you paste, and everything the model writes back, is counted.

Next-token prediction

At each step the model produces a probability distribution over every possible next token, picks one, appends it, and runs again with the longer text. That is the whole generation loop.

The model is optimising for what plausibly comes next, given everything before it. It is not optimising for what is true, what compiles, or what exists. When the plausible thing and the true thing coincide — which is often — the output is excellent. When they diverge, the output is confidently wrong.

This single sentence explains most of what follows: the model is a plausibility engine, not a truth engine. Every prompting technique in this session is a way of making the true answer also the most plausible one.

Context window

The context window is the total amount of text — your instructions, the code you pasted, the conversation history, and the response being written — that the model can consider at once. It is finite.

  • Nothing outside the window exists. A file you did not paste is not "missing"; from the model's position it was never mentioned.
  • Long conversations degrade. As a chat grows, early instructions compete with a large volume of later text. Constraints given twenty messages ago quietly stop being honoured.
  • More context is not automatically better. Pasting an entire project buries the three relevant functions among hundreds of irrelevant ones. Precision beats volume.
  • Fresh chat for a fresh task. A new problem in an old, cluttered conversation inherits all of that clutter.

Temperature

Temperature controls how the next token is chosen from the probability distribution. Low temperature concentrates on the highest-probability tokens. High temperature flattens the distribution and allows less likely choices.

Low · near 0

Focused, repeatable

The same prompt gives near-identical output. Correct default for code, refactoring, data transformation, anything with a right answer.

Medium

Balanced

Normal conversation, explanation, documentation. Enough variation to phrase things well without wandering.

High

Varied, surprising

Brainstorming names, generating varied test data, exploring alternative approaches. Not for code you intend to keep.

Chat interfaces usually do not expose this control, but the behaviour is still visible: ask the same question twice in two fresh chats and compare. Low temperature does not mean correct. It means consistent. A model can be consistently wrong.

Part 2 · Failure mode

Why models hallucinate

A hallucination is not a malfunction. It is the generation loop working exactly as designed, in a region where the plausible answer and the real answer are not the same thing.

When a model has seen thousands of examples of array.someMethod() patterns, a method name that fits the pattern is highly probable — whether or not that method exists. The model has no mechanism to check. It cannot run the code, open the docs, or fail to find something.

The four shapes hallucination takes in code

Shape 1

Invented APIs

A method, hook or utility that does not exist, but sits perfectly inside the naming conventions of a real library. Frequently the most useful-sounding function in the answer.

Shape 2

Real API, wrong signature

The function exists. The argument order, option names, or return shape are subtly wrong — often matching an older or newer version than yours.

Shape 3

Confident factual claims

Complexity analysis, browser support, version behaviour, performance comparisons — stated in the same assured tone as everything else, with no signal of uncertainty.

Shape 4

Fabricated specifics about your code

Referring to fields, props, files or functions you never showed it. The model fills the gap you left with something reasonable.

Live demonstrations

Demo A · character-level blindness
How many times does the letter "r" appear in "refactoring"?
What to watch for: the answer arrives instantly and confidently. The model never saw the individual characters — it saw two or three tokens.
Demo B · invented API
Which built-in React hook should I use to debounce a value so my search input does not fire on every keystroke?
What to watch for: pressure toward a built-in answer where none exists. A confident, well-named, non-existent hook is a common result.
Demo C · fabricated specifics
Fix the bug in my ProductCard component where the price is not displaying.
What to watch for: no component was provided, yet the answer names props and fields with total assurance. Everything after the first line is invention.
Demo D · confident wrong analysis
What is the time complexity of the algorithm below? Answer in one line. function mystery(arr) { let out = []; for (let i = 0; i < arr.length; i++) { if (out.includes(arr[i]) === false) out.push(arr[i]); } return out; }
What to watch for: the hidden cost of includes inside the loop makes this quadratic. A quick, plausible "O(n)" is a common answer, and it reads exactly as confidently as a correct one.

The tell is that there is no tell. A hallucinated answer is written with the same fluency, structure and confidence as a correct one. Tone carries no information about accuracy. The only defence is verification.

What reduces it

  • Supply the ground truth. Paste the actual code, the actual error, the actual data shape. The model cannot invent what you have already specified.
  • Name versions explicitly. "React 18", "Java 17", "Express 4" removes an entire class of version-mismatch errors.
  • Give permission to not know. Asking it to say when it is unsure, or to flag which parts need verification, changes what it produces.
  • Ask for verifiable output. Something you can run, compile or check beats something you can only read and nod at.
  • Prefer familiar territory. Widely used, stable libraries produce far fewer inventions than niche or fast-moving ones.
Part 3 · Judgement

Where AI is reliable, and where it is risky

The useful question is never "is AI good at coding". It is "can I cheaply verify this particular output, and what happens if it is wrong".

Two axes decide it

Axis 1

Verification cost

How long does it take you to know the output is correct? Running a function takes seconds. Confirming an authorisation rule is watertight takes real effort. Low verification cost makes AI safe even when it is often wrong.

Axis 2

Cost of being wrong

A malformed test file wastes a minute. A subtly wrong interest calculation or an access-control gap can reach production and cause real damage. High blast radius demands human authorship.

TaskVerdictWhy
Explaining unfamiliar codeReliableYou still read the code afterwards; errors surface immediately.
Boilerplate and scaffoldingReliableHighly patterned, and it either runs or it does not.
Syntax translation between languagesReliableStructure is preserved; mistakes are visible on reading.
Regex and string transformationsReliableInstantly testable against your own examples.
Decoding an error message or stack traceReliableYou have the ground truth in hand and can confirm the fix.
Test scaffolding and edge-case suggestionsReliableTests are self-checking; a wrong test fails loudly.
Naming, docs, commit messagesReliableYou are the judge, and the cost of a bad suggestion is zero.
Exact API signatures and optionsVerifyClassic invention territory. Confirm against real documentation.
Version-specific behaviourVerifyTraining data blends versions. Always state yours.
Performance and complexity claimsVerifyPlausible reasoning, unverified conclusions. Measure instead.
Large multi-file refactorsVerifyToo much changes at once to review honestly. Break it up.
Authentication and authorisation logicRiskyFailures are silent, and the blast radius is the whole system.
Business rules unique to your productRiskyThe model has never seen your rules. It will produce a generic guess.
Financial or regulatory calculationsRiskyWrong answers look right and carry real consequences.
Anything involving real credentials or customer dataRiskyNever paste it. Covered under non-negotiables.
Learning a fundamental you will be assessed onRiskyThe output is correct and you still cannot do it. The cost arrives later.

A useful reframing: AI raises your ceiling, never your floor. It makes a strong engineer faster at things they could already check. It does not make an engineer who cannot review the output safer — it makes them faster at shipping things nobody has reviewed.

Part 4 · Structure

The anatomy of a working prompt

Four components. Not every prompt needs all four, but when output is disappointing, the cause is almost always a missing one.

01

Role

Who the model should answer as. Sets vocabulary, depth and assumptions.

"You are a senior React developer reviewing code from a junior teammate."

02

Context

Everything the model cannot see: the code, the error, the data shape, the versions, the conventions, what you already tried.

The component that breaks, and the exact console output.

03

Task

One specific thing to do, stated as an action. Not a topic, not a wish.

"Identify why the list re-renders on every keystroke and fix it."

04

Output format

The exact shape you want back. Removes the guesswork about how much, in what form, with what around it.

"One code block, no explanation before or after, comments only where the logic is non-obvious."

Same task, with and without the structure

Unstructured
write a search bar in react
What comes back: a generic component with an invented data source, arbitrary styling, a state pattern you may not use, and three paragraphs of explanation you did not ask for. Nothing about it fits your project.
Structured
You are a senior React developer writing code for a beginner-friendly codebase. CONTEXT - React 18, function components, plain CSS. No TypeScript, no Tailwind, no external libraries. - State is managed with useState only. No useEffect in this component. - The parent already holds the full list and passes it down. - Props: items (array of { id, name, category, price }), onSelect (function). TASK Write a SearchableList component that renders the items and filters them as the user types in a text input. Matching is case-insensitive on name only. CONSTRAINTS - Do not fetch data. Filter the items prop. - Do not mutate the items prop. - Show a message when nothing matches. - Every list item must have a stable key. OUTPUT FORMAT One code block containing the complete component. No prose before or after. Add a comment only where the logic is not obvious from the code.
What comes back: code that drops into the project unmodified, uses only patterns already in use, and can be reviewed in under a minute because you already know what it should look like.

The structured version takes about ninety seconds to write. It replaces four rounds of "no, not like that" — and more importantly, it forces you to decide what you actually want before asking, which is where most of the value sits.

Part 5 · Iteration

The refinement ladder

One task, six rounds. Each round adds a single element, and the change in output is attributable to that element alone.

The task: a component that shows a list of items with a search box and a sort control.

Round 1 · bare task
make a list with search and sort
Result: unusable. No language specified, no framework, no data. The model picks all of it for you, and it picks wrong.
Round 2 · + stack and versions
Write a React 18 function component that renders a list of items with a search box and a sort control. Plain CSS, no libraries.
Result: runnable React, but with invented data hardcoded inside, and possibly hooks or patterns the codebase does not use. Change: the stack is now fixed.
Round 3 · + the real data shape
... as above ... The component receives this prop: items: [ { id: 1, name: "Laptop Stand", category: "accessories", price: 1299 }, { id: 2, name: "Mechanical Keyboard", category: "input", price: 4599 } ] Search filters on name. Sort toggles between price ascending and descending.
Result: the field names are now correct. This single addition eliminates the most common category of unusable output — code written against a data shape that does not exist. Change: no more invented fields.
Round 4 · + constraints
... as above ... CONSTRAINTS - useState only. Do not use useEffect. - Do not mutate the items prop when sorting. - Do not fetch anything. - Handle the empty-results case. - Stable key on every list item.
Result: the two bugs that would otherwise have appeared — an in-place .sort() mutating the prop, and an unnecessary effect — are now prevented rather than corrected later. Change: known failure modes closed off in advance.
Round 5 · + role and output format
You are a senior React developer writing code for a beginner-friendly codebase. Prefer clarity over cleverness. ... context, task and constraints as above ... OUTPUT FORMAT One code block, complete component, no prose before or after. Comments only where the logic is not obvious.
Result: readable code at the right level, delivered in a form you can copy directly. Change: tone, complexity and packaging are now controlled.
Round 6 · targeted follow-up
Keep everything else identical. Two changes: 1. Search should also match category, not just name. 2. Pull the filter-and-sort logic into a helper function above the component so it can be tested independently. Return only the changed parts, not the whole file.
Result: a small reviewable diff instead of a fresh rewrite. Change: iteration is now surgical, which means review stays honest.

What the ladder teaches

  • Change one thing per round. If you add context, constraints and a role simultaneously and the output improves, you have learned nothing about which mattered.
  • "Keep everything else identical" is the highest-value phrase in iterative prompting. Without it, follow-ups silently rewrite parts you had already accepted.
  • Ask for changed parts only. A full re-emission of the file makes it impossible to see what actually moved.
  • Restart rather than repair. After three or four failed rounds, the conversation is polluted with rejected attempts. A fresh chat with everything you have learned folded into round one beats a fifth correction.

The same ladder in Java

The technique is not language-specific. The identical progression applies to a backend task — and the components map one for one.

Java equivalent, fully specified
You are a senior Java developer writing code for a beginner-friendly codebase. CONTEXT - Java 17. No Lombok, no external libraries beyond the JDK. - Existing record: record Item(int id, String name, String category, int price) {} - Callers pass an unmodifiable List<Item>. TASK Write a utility class ItemFilter with one public static method that filters items by a case-insensitive substring match on name or category, then sorts by price. Sort direction is a parameter. CONSTRAINTS - Do not modify the input list. - Return an empty list rather than null when nothing matches. - Handle a null or blank search term by returning everything, sorted. OUTPUT FORMAT One code block. No prose. Javadoc on the public method only.
The point: role, context, task, constraints, output format — same five parts, different stack. The structure is the transferable skill; the syntax is not.
Part 6 · Consistency

Constraints and few-shot examples

Describing a style is unreliable. Demonstrating it is reliable. When output needs to match an existing convention, examples beat adjectives every time.

Zero-shot vs few-shot

Zero-shot

Instruction only

You describe what you want. Correct default for most tasks — it is faster and the model is genuinely good at following clear instructions.

Few-shot

Instruction plus two or three worked examples

You show what you want. Worth the extra tokens when the output must match a specific format, house style, or existing convention.

Demonstration: enforcing a house style

The goal is DSA solutions in a fixed format — a required header comment block, a specific function signature, and a complexity note in a set position.

Zero-shot · described style
Write a function to check if a string is a palindrome. Use our standard format with a header comment, clear naming, and complexity analysis at the end.
Result: some kind of header, some kind of complexity note, in some position. Ask three times and get three different layouts. "Our standard format" means nothing to a model that has never seen it.
Few-shot · demonstrated style
Write solutions in exactly this format. Two examples follow. EXAMPLE 1 /** * Problem: Two Sum * Approach: Single-pass hash map storing complements. */ function twoSum(nums, target) { const seen = new Map(); for (let i = 0; i < nums.length; i++) { const need = target - nums[i]; if (seen.has(need)) return [seen.get(need), i]; seen.set(nums[i], i); } return []; } // Time: O(n) | Space: O(n) EXAMPLE 2 /** * Problem: Maximum Subarray * Approach: Kadane's algorithm, running local and global maxima. */ function maxSubArray(nums) { let best = nums[0]; let current = nums[0]; for (let i = 1; i < nums.length; i++) { current = Math.max(nums[i], current + nums[i]); best = Math.max(best, current); } return best; } // Time: O(n) | Space: O(1) NOW SOLVE Problem: Valid Palindrome — ignore non-alphanumeric characters and case. Follow the format above exactly. No prose outside the code block.
Result: the header block, the comment fields, the trailing complexity line and its exact separator all match. Run it five times and the shape is stable. Two examples are usually enough; a third helps when the pattern has variation the first two do not show.

The practical version of this at work: when adding a file to an existing codebase, paste one similar existing file as the example. You are not asking for good code in the abstract — you are asking for code that looks like it belongs.

Constraints that consistently earn their place

  • Negative constraints. "Do not use external libraries." "Do not use TypeScript." "Do not add error handling I did not ask for." Naming what to avoid is often more effective than naming what to do.
  • Scope limits. "Change only the function I pasted." "Do not restructure the file." Prevents unrequested rewrites.
  • Length and shape. "Under 40 lines." "One code block." "No explanation."
  • Level. "Written for someone three months into React." Controls how clever the solution gets.
  • Uncertainty handling. "If a detail is missing, ask instead of assuming." Converts silent invention into a question you can answer.
Part 7 · Reasoning

Chain of thought

Asking for reasoning before the answer changes the answer. It also costs time and tokens, so it belongs on some tasks and not others.

Because output is generated one token at a time with each token conditioned on the ones before it, text that works through the problem gives later tokens something better to condition on. Reasoning written first genuinely improves what comes after — it is not a formality.

Worth it

Multi-step and diagnostic work

  • Debugging where the cause is not obvious
  • Choosing between design approaches
  • Tracing why a value ends up wrong
  • Anything with several interacting conditions
  • Complexity analysis, done properly
Not worth it

Pattern work with a known shape

  • Boilerplate and scaffolding
  • Syntax conversion
  • Renaming and formatting
  • Simple, well-specified components
  • Anything where you already know the answer's shape
Reasoning first, then the fix
Before writing any code, work through this in order: 1. State what the code currently does, line by line, for the input given. 2. Identify the exact point where actual behaviour diverges from expected. 3. Explain the root cause in one or two sentences. 4. Only then, give the corrected code. Do not skip to step 4.
Why the last line matters: without it, the model frequently jumps straight to a plausible fix and the reasoning steps become a retroactive justification of a guess.

Reasoning that reads convincingly can still reach a wrong conclusion. Chain of thought improves the odds and makes the mistake visible — you can now see which step went wrong. It does not make the answer verified.

Part 8 · Application

Developer prompting patterns

Five recurring tasks, each with a prompt shape that reliably works.

Pattern 1 — Explaining code

Explain
Explain the code below to someone comfortable with JavaScript but new to React. Structure the explanation as: 1. What this component does, in two sentences. 2. What each hook and handler is responsible for. 3. The order things happen when the user types in the input. 4. Anything here that would surprise someone new to React. Do not suggest improvements. I only want to understand it. [paste code]
Why it works: the audience level controls vocabulary, the numbered structure controls organisation, and the last line prevents the answer drifting into a code review you did not request.

Pattern 2 — Generating boilerplate

Scaffold
Generate the starting file for a new React component following the conventions in the example file below. Component name: OrderSummary Props: orders (array of { id, total, status }), onCancel (function) Behaviour: render each order; show a Cancel button only when status is "pending". Match the example's import order, export style, prop handling and file structure exactly. Same stack: React 18, plain CSS, useState only. EXAMPLE FILE [paste one existing component]
Why it works: the example carries every convention you would otherwise have to describe and would probably describe incompletely.

Pattern 3 — Writing tests

Test
Write unit tests for the function below. Before writing them, list the edge cases you intend to cover and wait for me to confirm. Constraints once confirmed: - Plain Jest, no extra libraries - One assertion per test where reasonable - Test names describe behaviour, not implementation - Cover empty input, single element, duplicates, and invalid input [paste function]
Why it works: the pause is the valuable part. The edge-case list is often more useful than the tests themselves, and reviewing it costs ten seconds while reviewing twenty generated tests costs ten minutes.

Pattern 4 — Debugging

Debug
A bug I cannot locate. EXPECTED: the list filters as I type. ACTUAL: the input accepts one character, then loses focus, and the list does not filter. EXACT ERROR (browser console): [paste the full message and stack, unedited] CODE (the whole component, unmodified): [paste] ALREADY TRIED: - Confirmed the items prop arrives correctly (logged it) - Removing the key prop changed nothing Environment: React 18.2, Vite dev server, Chrome. Give the most likely root cause first with your reasoning, then the fix. If you need to see another file to be sure, say which one instead of guessing.
Why it works: expected versus actual defines the target, the unedited error is the ground truth, "already tried" prevents the first two suggestions being things you have done, and the last line converts invention into a request.

Pattern 5 — Refactoring

Refactor
Refactor the function below for readability only. RULES - Behaviour must be identical. Same inputs, same outputs, same errors. - Do not rename anything exported. - Do not change the file structure or add dependencies. - Do not add features, validation or error handling. After the code, list each change you made and why, one line each, so I can review them individually. [paste function]
Why it works: refactoring prompts fail by quietly changing behaviour. The rules block that, and the change list makes review a checklist rather than a diff hunt.
Part 9 · Context

Giving the right context

The single highest-leverage skill in this session. Most disappointing output is not a model failure — it is a context failure.

The model knows only what is inside the context window. Every gap you leave is filled with something plausible and generic. Deciding what to include is the actual work.

What counts as context

  • ERRORThe exact error output, unedited. Full message, full stack trace, the line it points to. Paraphrasing an error — "it says something about undefined" — throws away the most information-dense text you have.
  • DATAThe real shape of your data. A sample API response, a props list, a record definition, a config object. This eliminates the most common cause of unusable code: correct logic written against field names that do not exist.
  • CODEThe surrounding code, not just the broken line. The whole function, the component it lives in, the caller. A bug is rarely on the line where it surfaces.
  • CONVYour conventions. One existing file that does something similar communicates naming, structure, import order and style more completely than a paragraph describing them.
  • VERVersions and environment. React 18, Java 17, Node 20, which build tool, which browser. Removes an entire class of confidently outdated answers.
  • DIFFExpected versus actual. Both halves. "It does not work" describes a feeling; "expected X, got Y" describes a problem.
  • TRIEDWhat you already ruled out. Otherwise the first suggestions are the things you spent an hour eliminating.
  • LIMITConstraints you are working under. Cannot change the API, cannot add dependencies, must keep the existing signature, must work on old browsers.

Same bug, two prompts

No context
my react app crashes when the data loads, how do I fix it
Result: a list of five generic possibilities, none specific to your code, and confident references to components and props that were never mentioned. You now have to test five guesses.
With context
EXPECTED: the product list renders once data arrives. ACTUAL: white screen the moment the fetch resolves. CONSOLE (exact): Uncaught TypeError: Cannot read properties of undefined (reading 'map') at ProductList (ProductList.jsx:14:23) API RESPONSE (actual, from the Network tab): { "status": "ok", "data": { "products": [ { "id": 1, "name": "Laptop Stand", "price": 1299 } ] } } COMPONENT (unmodified, full file): [paste] ALREADY TRIED: confirmed the request returns 200 and the payload above. Environment: React 18.2, Vite, fetch in a useEffect. Identify the root cause, then give the minimal fix. Do not restructure the component.
Result: the mismatch between the response shape and what the component reads is immediately visible in the context provided. The answer is specific, correct, and checkable in seconds.

Precision beats volume

Pasting more is not the same as pasting better. Three relevant files beat thirty. Signs you have pasted too much: the answer addresses code you did not ask about, earlier constraints stop being honoured, or the response becomes vague and hedged. Signs you have pasted too little: the answer references things you never mentioned, or opens with a list of assumptions.

Before pasting anything, check what is in it. API keys, connection strings, tokens, customer records, internal URLs, proprietary business logic. Context is the most valuable thing you give a model and the most dangerous. This is covered in full under non-negotiables.

Part 10 · Diagnosis

Anti-patterns

Six prompts that fail. The flaw in each is named after the prompt — worth attempting the diagnosis before opening it.

1  ·  "make my code better"
Vague ask. "Better" is undefined — faster, shorter, more readable, more testable, safer? The model picks one at random, usually by rewriting everything. Fix: name the single dimension and the boundary. "Reduce this function to under 30 lines without changing behaviour."
2  ·  "write a react component for a product page and also set up routing and add authentication and write the tests and explain everything"
Overloaded prompt. Five tasks in one request. Quality drops across all of them, the response is too large to review honestly, and correcting one part forces a regeneration of the rest. Fix: one task per prompt, in sequence, reviewing each before the next.
3  ·  "why isn't my useEffect working"
Missing context. No code, no error, no expected-versus-actual. The model answers about useEffect in general, which you could have read in the docs. Fix: the component, the exact console output, what you expected, what happened, what you already tried.
4  ·  "fix the bug in the checkout function"
Assumed context. Referring to code the model has never seen. It will not say "I cannot see that file" — it will invent a checkout function and fix a bug in the invention. Fix: paste it. Every time. Assume nothing carries over, including from earlier in the same chat once it grows long.
5  ·  "write a function to sort products by price"
Missing constraints. Ascending or descending? Mutate or return a copy? What about equal prices, missing prices, string prices? The model chooses, and it commonly chooses in-place .sort(), which mutates your input. Fix: state the direction, the immutability requirement, and the edge cases before asking.
6  ·  "what's the fastest way to deep clone an object in javascript in 2026"
Wrong tool for the job. This is a current-facts-and-measurement question. The model's knowledge has a cutoff, performance depends on your data and runtime, and "fastest" cannot be answered without measuring. It will still answer confidently. Fix: use it to generate the benchmark, then run the benchmark.

The pattern behind the patterns

Every one of these is a version of the same mistake: assuming the model knows something it does not. Your intent, your codebase, your definition of better, your constraints, or the current state of the world. It never says "I do not have that." It produces something plausible in the shape of the gap.

Part 11 · Exercise

Rewrite worksheet

Five failing prompts. For each: name the flaw, rewrite it, and write one sentence on why the rewrite is better. No AI tool required — the rewriting is the skill being practised.

01

"add error handling to my api call"

Which call? What should happen on failure — retry, message, fallback, log? What does the rest of the codebase do?

02

"convert this to java"

Which Java version? Preserve structure or idiomatic rewrite? What about the JavaScript-specific behaviour that has no direct equivalent?

03

"my form doesn't submit"

Expected versus actual. Any console output. The form code. Already ruled out.

04

"write tests for this and also fix any bugs you find and improve the naming"

Three tasks. Which one first, and how do you review the result of all three at once?

05

"is my code secure?"

Secure against what? Which code? What is the threat you are worried about, and is this a question a model can answer definitively at all?

Marking your own rewrite

A rewrite is good when it satisfies all of these:

  • Someone unfamiliar with your project could act on it without asking a question.
  • It asks for exactly one thing.
  • Every piece of information the answer depends on is present in the prompt.
  • The output shape is specified.
  • You can tell, by reading the result, whether it followed the instructions.

The last one matters most. A prompt so vague that any output looks acceptable has not been improved — it has only been lengthened.

Part 12 · Close

Non-negotiables

Five rules. These do not change with tool, model, seniority or deadline.

01

Never ship code you have not read and understood

If you cannot explain each line, you cannot maintain it, review it, or debug it at 2am. The code carries your name in the commit history regardless of who wrote it.

02

Never paste secrets, credentials or customer data

API keys, connection strings, tokens, real customer records, internal system details, proprietary business logic. Once it leaves your machine you do not control it. Replace with realistic dummy values before pasting.

03

Always run and test what it writes

Reading is not verification. Code that looks correct and code that is correct are different things, and the gap is exactly where subtle bugs live.

04

Verify every API, method and factual claim

Especially the ones that solve your problem most conveniently. Confident tone is not evidence. Check the real documentation.

05

Do not outsource the fundamentals

Using AI on something you could not do yourself feels productive and leaves you exactly where you were. Interviews, incidents and design discussions all test the floor, not the ceiling.

Where an employer is involved

Follow your organisation's AI policy

Many companies restrict which tools may be used and what may be entered into them. These rules are the floor. Your workplace policy sits on top and always wins.
